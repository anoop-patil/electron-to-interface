# ElectronToInterface

Write a short Python program, click Run, and zoom in: from your code to its bytes, tokens, syntax tree and bytecode, then the interpreter's C code, the CPU instructions, the operating system and the pixels on your screen. Each zoom level explains what it shows in plain English, and says how it knows. Programs can be up to 20 lines and use any Python feature. Think *Powers of Ten*, for programming.

## What works today

- **The app** (`app/`) shows your program at all nine zoom levels. You type a program and click Run, and Python 3.14.2, running in your browser, shows your code, its bytes, its tokens, its structure and its bytecode, then the interpreter that runs it. Click a byte to see which character it stores, why, and its 8 bits. Click a token to see what kind it is, where it sits and which bytes make it up; the tokens include the ones that mark line ends and indentation. Level 4 shows the syntax tree Python builds from your code, as boxes inside boxes; click a box to see its role. On phones the tree is an indented outline. The text on every level comes from Templates filled in with your program's Facts, so it fits any program.
- Five Examples sit in a row of buttons above the editor: hello world, a for loop, a function called in a loop (greet.py), a list comprehension and a class. The page opens on hello world, ready to zoom through before Python has loaded: each Example's Analysis was made when the site was built, by the same Python run under Node.js. Picking an Example puts its code in the editor and shows it at once. Where the page would say your browser just ran something, an Example's says the same Python ran it when the site was built. You can type while Python loads; Run turns on once it is ready. A browser with no WebAssembly, or that reports under 1 GB of memory, doesn't load Python at all: it gets the Examples, with a note that Run is off.
- Level 5 lists the steps of your program and of each function in it, plain names first, with how many times each ran. Next, Back and Play follow the order the steps ran in, and a strip shows every step run; click any run of any step. After that run, the page shows each frame's plates (Python's stack) and variables, the caller's frame waiting under the one it called, and the objects they point to. The plates are replayed from the step runs with Python's rules, so they are labeled Derived. Each code object's recipe card shows its names, fixed values and variables. Where Python rewrote a step into a faster form, such as `LOAD_CONST_MORTAL`, the page says so: watching every step stops Python rewriting them, so that form comes from a second run of your program, unwatched.
- Level 6 is the Interpreter handoff: by default, CPython never compiles your code to CPU instructions; its interpreter, written in C, reads your steps and runs a piece of its own C code, a handler, for each. For the step run you pick, the page shows the key lines of CPython's `Python/bytecodes.c` for each handler that ran, each with a plain-English sentence and a link to those lines on GitHub, labeled Reference. On a run where a step rewrote itself, such as greet.py's second call, it shows the general form's lines, then the new form's. This works for two Examples, `print("Hello World!")` and greet.py, whose handlers were recorded with a debugger on every step run; for any other program, level 6 explains how it usually works, labeled Typical, until ticket 29.
- Level 7 shows the machine code of each handler that ran for the step run you pick, from the CPython 3.14.2 program for Linux on x86-64: how big it is, its key lines in the order they ran, each with its bytes, then every instruction that ran, in order, and the full listing with those highlighted. A debugger recorded every instruction that ran, and the numbers some of them changed, such as a reference count going from 3 to 2, so every number the notes state is real. For hello world, `LOAD_NAME`, `CALL` and `RETURN_VALUE` are explained line by line. A jump that could fall back to the general form, and didn't, is described as a check. A panel names the registers the handlers use, worked out by reading their code, so it is labeled Derived. This works for the same two Examples; for any other program, level 7 explains how it usually works, labeled Typical, until ticket 30.
- Level 8 follows one line of output from your program to the terminal, as on a typical Linux terminal, in five stages: print hands its pieces to `sys.stdout`; they become bytes and wait in a small buffer; Python asks the operating system to write them, with a system call through door 1; the operating system passes them on; and the terminal app draws them. It follows the line the selected step run printed, and you can pick any other, including the lines of a traceback, which go out through door 2, in color. The pieces are recorded as your program runs, so they are labeled Observed; a traceback's are Derived, since Python writes it after your program stops, colored for a terminal. Which system calls carry them is worked out with Python's rules for a terminal: it sends what is waiting when a piece holds a newline, on a flush, or when its 131,072-byte buffer is full, as strace showed on our test machine. The rest is labeled Typical. A panel shows your program's three doors (file descriptors).
- Level 9 shows how a terminal draws one character of a line of output, labeled Typical. You pick the line, as at level 8, then a character in it, and follow it from its bytes to pixels. Your browser draws the line just now, in your screen's own pixels, and the page enlarges the character until each pixel is a square, with the font's outline on top: some pixels are fully lit, and the ones the outline only partly covers get a shade of gray (anti-aliasing). The page counts them. A space lights none. The page also says how many pixels your screen has, from what your browser reports.
- Whatever you pick at one level stays picked as you zoom: each level selects what is closest to it, so a byte of `print` leads to its token, its box and the step that finds `print`, and back. The editor highlights the code it comes from. A step run picked at level 5 stays picked through levels 6 and 7, and levels 8 and 9 follow the line of output it printed; a line picked at level 8 or 9 stays picked between them, and leads back to the step run that printed it.
- Each zoom level says how it knows what it shows, with an Honesty label such as Observed. Highlighted words open short Concept cards inside the app, and the Concepts button in the header lists them all.
- When you click Run, your program runs. The Terminal, under the editor, shows what it printed, and the traceback if it stopped with an error. While it runs, Python records each line, call, return and error (Events) and every bytecode step that ran, in order (step runs), with the line of output each step printed. Level 5 shows the step runs. A long run keeps the first 2,000 of each, and the Terminal and level 5 say so. A program that never ends, such as `while True: pass`, leaves Run waiting until ticket 20 adds a time limit.
- Under the Terminal, the Machine map shows your computer: disk, RAM, CPU, operating system and screen. It lights the part that holds what you're looking at: at levels 1 to 4, RAM, because the app keeps your program in memory and never saves it to your disk; at level 5, your steps, the plates and the objects, with how many there are after the selected step run; at level 6, Python itself, running the C code for the selected step run; at level 7, the CPU running its machine code, with the registers and cache; at level 8, the operating system, and RAM while the line's bytes wait in Python's buffer; at level 9, the screen, with its size in pixels. Each part opens its Concept card. The map is labeled Typical: it shows how computers usually work, and yours may differ. On phones the map is folded away behind "Your computer: where is everything?".
- Each of levels 1 to 8 has a Try it yourself section: a command to run on your own computer, for your program saved as `program.py`, with tabs for what each part does, what it shows and how to read it. What it shows is real: when you click Run, Python in your browser does what the command does, on your program (for an Example, the same Python did it when the site was built), so you see your program's own output, its bytes as a list of numbers, its tokens as `python -m tokenize` lists them, its syntax tree as `python -m ast` prints it, its bytecode as `python -m dis` shows it, the faster forms its steps had become after it ran, or how long it took. Your browser's clock is coarse and runs Python as WebAssembly, so level 7 also shows the same timing run natively on our test machine, labeled Reference. Level 8's command, `strace`, can't run in a browser: it shows the pieces your program handed to `sys.stdout` and `sys.stderr`, observed, and what strace printed for hello world or greet.py on our test machine, labeled Reference. Level 9's has no command: it says how to see your screen's red, green and blue subpixels.
- You can move through all nine zoom levels with the depth gauge, the Zoom in and Back buttons, the ↓ and ↑ keys, or the address bar (`/zoom/1` to `/zoom/9`). The app has light and dark themes and works on phones. Tickets 01 to 16 and 32, of 32, are done.
- **The prototype** (`prototype/hello-zoom-v8.html`) shows all nine zoom levels for one 5-line Example, `prototype/examples/greet.py`. Open the file in a browser. `hello-zoom-v7.html` is the earlier hello-world version.

## Run the app

You need Node.js 24 and Python 3.14.

```
cd app
npm install
npm run dev
```

Open the address it prints. Hello world shows straight away; Run turns on once Python has loaded, which takes a few seconds. Starting the dev server or a build also runs the analyzer on each Example, which takes a few seconds more.

To run the tests (GitHub Actions runs all of them on every push):

```
cd app
npm run typecheck
npm test                          # Vitest: the analyzer running in real Pyodide
npx playwright install chromium   # once
npm run test:e2e                  # Playwright: the page in a real browser
pip install -r requirements-dev.txt
python -m pytest                  # pytest: the analyzer on CPython, and the Reference Library's Examples
```

## How the app is built

- `app/analyzer/analyze.py` is the Python that turns a program into an Analysis: the Facts that the zoom levels show. It saves the program as `program.py` in Python's in-memory files and runs it once as `python program.py` would, recording its output, each piece it hands to `sys.stdout` and `sys.stderr`, and its Events and step runs with `sys.monitoring`, and replaying each frame's plates as the steps run. Then it runs each Try it yourself command on the same file (`python FILE`, `python -c` or `python -m`), recording what the command printed; after `python program.py`, it records the form each step had become. It lists the program's tokens with `tokenize`, its syntax tree with `ast` and its bytecode with `dis`. It runs in Pyodide (CPython compiled to WebAssembly) inside a Web Worker. Your code is analyzed in your browser and never sent anywhere, and the site serves Pyodide's files itself rather than from another site.
- The Examples are in `app/examples/`, except greet.py, which is `prototype/examples/greet.py`; `app/src/examples/examples.ts` lists them. When the build or the dev server starts, `app/src/examples/build.ts` runs the analyzer on each one in Pyodide under Node.js, checks the Analysis against the schema, and writes it to `app/public/examples/`, which the site serves as static files. The build fails if one breaks the schema.
- `app/schema/analysis.schema.json` defines the Analysis, the Template format and the Reference Library. The TypeScript types in `app/src/generated/` are generated from it: after editing the schema, run `npm run gen:types`.
- `app/templates/py314.json` holds the Templates for Python 3.14: the text of each explanation, with slots such as `{value}` for Facts. It also holds each zoom level's Try it yourself command and its text. `app/src/explain/` fills them in.
- `app/concepts/cards.json` holds the Concept cards and the Concepts index. `app/concepts/honesty-labels.json` holds the set of Honesty labels and which one each zoom level and panel carries, so changing the set is a data edit.
- `app/reference/cpython-3.14.2.json` is the Reference Library: lines of CPython's C source for each handler, keyed by how it ran (`CALL/python`, `CALL/rewrites`), each with a plain-English sentence; the machine code of every handler the Examples ran; and, for the Examples, which handlers ran on each step run, every instruction each ran, and the numbers it changed, with the timing and strace samples levels 7 and 8 show. `app/reference/example_runs.py` derives those from the gdb, timing and strace captures and the disassembly in `prototype/data/` and checks they line up with the analyzer's step runs. `app/reference/cpython-3.14.2/Python/bytecodes.c` is a copy of that file at CPython's tag v3.14.2.
- The build fails if a Template, a card, the labels or the Reference Library break the schema, if a Template names a Fact that doesn't exist, if any text opens a card that doesn't exist or puts a slot inside a card's words, or if a quoted line of C isn't at its line numbers in the copy of `bytecodes.c`, whose SHA-256 it also checks, or if a note on a machine instruction states a number the debugger didn't record and the instruction doesn't hold.
- `app/src/` is the React page. `app/src/zoom/` holds the zoom levels, the depth gauge and the navigation between levels; `selection.ts` links each level’s elements to the others through Fact IDs, so a new level adds its entry there. `app/src/editor/` holds the editor. `app/src/terminal/` holds the Terminal. `app/src/machine/` holds the Machine map: `mapState.ts` says what each zoom level lights, so a new level adds an entry there and leaves the map alone.
- Components are styled with Tailwind classes. `app/src/styles.css` holds the design tokens, CSS variables with a light and a dark value each, and Tailwind's theme reads its colors and fonts from them.
- The site serves its fonts, IBM Plex Sans and Mono, itself.

## Where the prototype's facts come from

Everything the prototype labels Observed or Reference was captured on Linux x86-64 with CPython 3.14.2 (python-build-standalone release 20251205). The scripts in `prototype/tools/` reproduce it:

- `extract-machine-code.sh` disassembles the interpreter's handlers for each hello-world step.
- `trace-handler-paths.sh` records, with gdb, which of those instructions actually run, and the number each inc and dec instruction changed. It also times hello world, and lists its write system calls with strace.
- `capture-example.sh greet` captures everything v8 shows for an Example: bytes, tokens, syntax tree, bytecode, its write system calls, the order the steps ran in, which handler ran on each run of each step (gdb, 3 identical runs), and those handlers' machine code.
- `build-hello-zoom-v8.py` builds `hello-zoom-v8.html` from its template and that data.
- `check-c-refs.mjs` confirms that every quoted line of CPython C source sits at the line number shown.

The shell scripts run on Linux or WSL. They download what they need into `/tmp` and install nothing, but gdb needs libraries a desktop Ubuntu has, such as libpython3.14; on a bare system, install the `gdb` and `strace` packages first. GitHub Actions reruns them in Ubuntu 26.04 whenever they or their data change, and `compare-data.py` fails the run if they don't reproduce the committed data.
